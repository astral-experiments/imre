# Calling google-crc32c from a rebuilt wheel

Imre and CPython both compiled the unchanged C extension from google-crc32c
1.8.0. The direct C program, the CPython extension, and the Imre wheel linked
the same Google CRC32C 1.1.2 release archive. The timed Python program used
ordinary `from google_crc32c import value, extend` calls. Imre compiled the
consumer in a separate directory containing only the entry script and found the
package under pip's installed wheel directory. [Reproduction](../../examples/google_crc32c/README.md) · [Source hashes](../../examples/google_crc32c/UPSTREAM.json)

| Method | Bytes per call | Direct C | CPython | Imre | Imre / C |
| --- | ---: | ---: | ---: | ---: | ---: |
| `value` | 8 B | 4.87 ns | 88.47 ns | 82.95 ns | 17.04× |
| `extend` | 8 B | 8.31 ns | 96.79 ns | 93.36 ns | 11.23× |
| `value` | 4 KiB | 174.51 ns | 261.06 ns | 256.73 ns | 1.47× |
| `extend` | 4 KiB | 177.49 ns | 266.08 ns | 261.73 ns | 1.47× |
| `value` | 1 MiB | 46.63 µs | 47.14 µs | 46.90 µs | 1.006× |
| `extend` | 1 MiB | 46.14 µs | 46.88 µs | 46.63 µs | 1.011× |

These are medians of 15 batches with one warm-up per process, pinned to CPU
26 on an AMD EPYC Milan Linux VM. Each process reused its buffer. Eight-byte
batches made 2,000,000 calls, 4 KiB batches made 32,768 calls, and 1 MiB
batches made 128 calls. `extend` fed each result into the next call.
The harness timed each batch from its request to its result and rotated process
order. It excluded startup and imports and verified the checksum on every batch.
The build used Clang 18.1.3, CPython 3.12.13, and whole-program Imre at
`-O3`. [Raw samples, artifact hashes, and profiles](2026-10-23-google-crc32c.json)

## Small calls

Callgrind counted 1,007 instructions per 8-byte `value` call in Imre and 67
in the C driver. For `extend`, the counts were 1,130 and 64. The counts subtract
an idle process from a batch of 50,000 calls and include the language-level loop.
In Imre's `extend` profile, `PyArg_ParseTuple` itself executed 124 instructions
per call, hashing the module-cache key spent 44 in the hash function, and the
SSE4.2 checksum function spent 45.

The initial bridge allocated and freed a 48-byte argument tuple on each call.
Reusing a uniquely owned tuple reduced Imre's median from 95.18 to 82.95 ns
for `value` and from 121.67 to 93.36 ns for `extend` across the two runs.
DHAT reported exactly the same 35 allocations and 92,316 bytes for 1,000 and
21,000 calls in the final Imre executable. Direct C used four allocations
and 81,928 bytes at both counts. Larger calls spend most of their time in the
shared native core.

## Upstream validation

All 42 unchanged upstream pytest cases passed on the rebuilt CPython extension.
All 42 also passed with the original Python wrappers running on CPython and the
compiled Imre executable providing the native functions. That run made 45
`value` and 224 `extend` calls, which the native worker acknowledged. This
exercises the original stream generator with upstream's mock streams. Pytest,
that generator, and the mock objects run on CPython in this test.

Separately, a native Imre consumer verified the typed wheel facade's checksum
construction, update, copy, digest, and hex digest. Both native extensions
matched three unsigned-mask cases including a negative seed and a 101-bit
integer. The upstream pure-Python fallback passed its 26 applicable cases.
The 16 cases selecting the C fixture require a native backend. [Test driver](../../tests/google_crc32c.py)
